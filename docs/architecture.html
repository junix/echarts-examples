ECharts Examples 架构文档

十二组精致的信息密度型 ECharts 可视化场景，带离线实机浏览器验证闭环

本项目是一组透明背景的 ECharts 可视化场景集合。每个场景独立成图，通过 URL 参数 ?scene= 切换，由 Playwright 在无头 Chromium 中逐屏导出 PNG 并做像素级质量校验。构建、渲染、验证三段式结构，确保每幅图都有真实内容且交互可用。

术语速览

Scene（场景）
一幅独立的 ECharts 图，由 id 标识，如 sankey、sunburst、knowledge-graph 等，共 12 个。
Catalog（目录）
catalog.json 中记录每个场景的分析用途、所属图族、复杂度与标签的元数据清单。
Stage（舞台）
页面中承载 ECharts 画布的 1400×900 透明 DOM 容器，id 为 stage。
VIS_READY
window.__VIS_READY__ 标志位，场景首帧渲染完成后置 true，供测试脚本等待。
Interaction Contract（交互契约）
指针移动或按下会递增 window.__INTERACTION_COUNT__，验证脚本借此确认图面可交互。
RGBA 质量断言
pngjs 逐像素扫描导出图，校验透明像素占比、可见像素占比与彩色像素数量，拒绝空白或单色输出。

核心特性

十二类图族全覆盖流、层次、多维、网络、矩阵、时序、金融、仪表、漏斗……覆盖 ECharts 主要系列类型。
透明呈现层背景全透明导出，便于嵌入任意设计系统、幻灯片或仪表盘底板。
离线实机验证Playwright 驱动本地 Chromium 无头渲染，不依赖在线服务与截图服务。
像素级质量门pngjs 逐像素校验透明占比、可见占比与彩色像素数，防止空白或损坏输出。
交互契约保证每个场景监听指针事件并计数，测试脚本模拟移动后断言计数增长。
零外部请求Playwright 路由拦截非本地请求，确保构建与渲染完全离线可重复。

一、系统分层架构

图 1 · 五层架构自底向上：目录定义场景元数据 → 场景声明图配置 → 渲染层输出画布 → 构建层打包 → 验证层闭环

整个系统由五层组成，自底向上分别是目录层、场景层、渲染层、构建层、验证层。每一层只依赖紧邻的下层，形成清晰的单向依赖链。

L1 目录
catalog.json — 场景元数据清单 12 条记录，每条含 id、分析用途 use、图族 family、分析问题 question、复杂度 complexity 与标签 tags。它是验证脚本的遍历来源，也是文档索引的唯一真相源。
L2 场景
12 组 EChartsOption 配置对象 在 main.ts 中以对象字面量形式定义，包括 sankey（能流）、sunburst（科研层次）、parallel（科考多维剖面）、knowledge-graph（气候知识图谱力导向）、treemap（产品组合风险）、calendar（运营异常日历）、candlestick（量价波动）、radar（航天器韧性对比）、heatmap（服务依赖热力）、gauge-cluster（系统健康仪表盘）、funnel（招聘漏斗）、river（文化主题河流）。共用一套 base 配置（透明背景、统一调色板、标题样式），各自差异化 series。
L3 渲染
ECharts Canvas 渲染器 + Stage 容器 1400×900 像素的透明画布，固定尺寸便于像素级比对。渲染完成后设置 window.__VIS_READY__ 标志，并在指针事件中递增 __INTERACTION_COUNT__，构成可被测试脚本观测的对外契约。
L4 构建
Vite + TypeScript → dist/ TypeScript 严格模式（strict），ES2022 目标，Bundler 模块解析。Vite 既做开发服务器，也生产打包。渲染时由 capture.mjs 以编程方式拉起 Vite 本地服务。
L5 验证
Playwright + pngjs 双保险 无头 Chromium 逐场景加载 → 等 VIS_READY → 透明背景截图 → 模拟指针移动校验交互计数 → pngjs 像素扫描（透明占比 >8%、可见占比 >3.5%、彩色像素 >2500）。任一条件不满足即报错退出。

二、场景族分类

图 2 · 12 个场景按六大图族分类，每个图族对应不同的分析问题与可视化形态

场景层并非一组零散的图，而是按分析问题的类型组织成六大图族。同一族内的场景共享相似的视觉语言（调色板、标题风格、透明呈现），但各自解决不同领域的问题——从能源流向到科研组合，从运营异常到文化主题变迁。

三、主走查：场景导出验证

以下选取「场景导出验证」这条端到端路径，展示从触发命令到产出验证通过的 PNG 文件之间，各模块如何协作。

图 3 · 主走查「场景导出验证」五步流程 + 逐场景循环

读取目录清单

capture.mjs 启动后读取 catalog.json，解析出 12 个场景 id。校验条目数不少于 12，缺失即抛错——防止目录被意外截断后静默通过测试。

构建并启动 Vite 服务

先执行 vite build 生产打包，再以子进程方式启动 Vite 开发服务器（监听 127.0.0.1 指定端口）。stdout 中检测到本地 URL 即视为启动成功，超时 15 秒则失败。

Playwright 加载场景

无头 Chromium 打开新页面，设置 1400×900 视口。路由拦截所有非本地/非 data: 请求，确保完全离线。访问 ?scene=<id>，等待 window.__VIS_READY__ === true（最多 15 秒）。

交互验证 + 透明截图

记录交互计数初始值，在 stage 上模拟两次鼠标移动，再读取计数——必须递增才算交互契约生效。随后对 #stage 元素执行 omitBackground 截图，保存为 out/<scene>-transparent.png。

像素级质量门

pngjs 读取导出的 PNG，逐像素统计完全透明像素、可见像素（alpha > 20）与彩色像素（RGB 最大最小差 > 24）。三项阈值（透明 > 8%、可见 > 3.5%、彩色 > 2500）任一不达标即报错，阻止劣质输出。

完成一个场景后，脚本关闭页面并进入下一场景，如此循环 12 次。全部通过后，关闭浏览器、终止 Vite 服务、正常退出。任何一步失败——无论是浏览器报错、交互不响应、还是像素质量不达标——都会立即抛出错误并终止测试。

四、验证层设计细节

图 4 · 验证层三道关卡：控制台零错误、交互契约触发、像素质量达标

验证层是本项目区别于普通示例集合的关键——它不是「能跑就行」，而是设置了三道并行的质量门。任何一道失败，整个测试立即终止。这样的设计确保每次代码变更后，12 个场景的视觉质量、交互可用性与运行时健康度都被自动守护，不会因重构或升级 ECharts 版本而悄悄退化。

为什么是这三道门？

Console Error 捕获运行时异常——ECharts 配置写错、数据格式不对、API 在新版本中变更，都会在控制台留下错误。这是最基础的健康检查。

交互契约 验证图面不仅是静态图片，而且能响应指针事件。这保证了 tooltip、emphasis、roam 缩放等交互功能真正可用，而不是渲染完就僵死。

RGBA 像素门 是最有特色的一道。它不检查具体像素值（那样会因渲染差异而脆弱），而是检查统计特征——透明占比保证背景确实透明（便于嵌入其他设计），可见占比保证图不是空的，彩色像素数保证画面有足够丰富的内容而非单色块。这种统计式断言比像素精确比对更健壮，又比「有图就行」更严格。

五、关键设计决策

透明背景
全透明呈现层，而非固定底色 选择 transparent 背景 + omitBackground 截图，是为了让导出图可以直接嵌入幻灯片、报告、任意品牌色的仪表板，无需二次抠图。代价是 RGBA 断言需要专门处理透明通道，但换来的是更高的复用价值。
固定尺寸
1400×900 固定画布，不随窗口缩放 Stage 使用 !important 固定宽高，ECharts init 也显式指定尺寸。这保证了像素级断言的稳定性，也确保每个场景的布局比例在不同环境下完全一致。对于示例集合，可复现的输出比响应式更重要。
离线隔离
Playwright 路由拦截，拒绝所有外部请求 capture.mjs 中 page.route 只允许 127.0.0.1、localhost 和 data: 协议通过。这确保测试完全离线可重复，不会因 CDN 波动、字体加载、第三方脚本等不可控因素影响结果。
单文件配置
所有场景集中在单个 main.ts 12 个场景的 option 都定义在同一个源文件里，而不是每个场景一个文件。对于示例集合项目，集中式配置降低了维护成本——统一调色板、统一 base 配置、方便横向比较不同图族的写法。代价是单文件较长，但每个场景独立且命名清晰，阅读成本可控。
